# HW1 — Optimizing a 1×1 Convolution through Data Layout

> **Note:** numbers marked `‹perf›` are placeholders to be filled from the `perf stat`
> run on the target Linux machine (see [run.sh](../run.sh)). The runtime figures are
> from a reference run and will be replaced by the final measurement.

## 1. General approach and thought process

I chose the **1×1 convolution** (a.k.a. *pointwise convolution*), the workhorse layer of
modern CNNs (MobileNet, ResNet bottlenecks, etc.). It is appealing for this assignment
because it is *arithmetically trivial* — just a weighted sum across channels — yet its
performance is **entirely dominated by how the data is laid out in memory**. That makes it
a clean vehicle for showing the hardware/software interplay: the math is fixed, so any
speedup must come from cache behaviour, prefetching, and vectorization rather than from
doing less work.

A 1×1 conv maps an input feature map `[Cin, H, W]` to `[Cout, H, W]` using weights
`[Cout, Cin]`:

```
out[co][h][w] = Σ_ci  in[ci][h][w] · weight[co][ci]
```

For every output pixel this is a dot product over the input channels. My plan was: write
the textbook version in the standard **NCHW** layout, profile it, identify the memory
bottleneck, and then attack *only that bottleneck* while keeping the output bit-identical.

Both versions are compiled with the **same flags** (`-O3 -march=native`) so the measured
difference is attributable to the optimization, **not** to the compiler. Inputs are
generated by an identical deterministic function in both programs, and each prints a
layout-independent checksum + sample values so correctness can be verified with a simple
`diff` (confirmed **identical**).

**Problem size:** `Cin = Cout = 512`, `H = W = 128`. This is deliberate: the input and
output tensors are ~32 MB each, which **exceeds the L3 cache**. If the data fit in cache,
the strided-access penalty would be hidden and the optimization would look pointless — the
effect only becomes visible (and meaningful) once the working set spills to DRAM.

## 2. Unoptimized implementation — [conv1x1_naive.cpp](../src/conv1x1_naive.cpp)

**Why I picked it.** It is the most natural way a student writes the layer: standard NCHW
layout, loop nest `(co, h, w, ci)`, accumulate, store. It is correct and readable — and
quietly cache-hostile.

**What it does.** Allocates the input (NCHW), weights (`[Cout][Cin]`), and output (NCHW),
fills them deterministically, then computes the convolution with the four nested loops, and
prints a checksum.

**Why it is not optimized.** The reduction loop runs over the input channel `ci`, but in
NCHW two consecutive channels of the *same pixel* are `H*W = 16384` floats — **64 KB** —
apart in memory:

```cpp
for (int ci = 0; ci < Cin; ++ci)
    acc += in[ci*HW + h*W + w] * wt[co*Cin + ci];   // in[] strides by 64 KB each step
```

Consequences at the hardware level:
- **Spatial locality is destroyed.** Each `ci` step touches a different cache line; most of
  the 64-byte line that gets fetched is never used before it is evicted.
- **The hardware prefetcher cannot help** — it locks onto unit-stride streams, not 64 KB
  jumps.
- **No vectorization** — the strided load forces scalar code (or an expensive gather).
- **No reuse** — the input is re-streamed from memory once per output channel (`Cout`
  times).

**Profiling results (naive):**

| Metric | Value |
|---|---|
| Runtime | ~6.4 s |
| Cycles | `‹perf›` |
| Instructions / IPC | `‹perf›` |
| L1-dcache load misses | `‹perf›` (expected: very high) |
| LLC load misses | `‹perf›` (expected: very high) |

## 3. Optimization — [conv1x1_opt.cpp](../src/conv1x1_opt.cpp)

**What I changed.** Two coupled changes, same math, identical output:

1. **Data layout NCHW → NHWC.** I transpose the input so that, for a fixed pixel, the `Cin`
   channel values are **contiguous**. The reduction over `ci` becomes a **unit-stride
   sweep**; the weight row `weight[co][·]` is contiguous over `ci` as well.
2. **Register blocking over output channels (4 at a time).** Each loaded input value `x` is
   reused across 4 output-channel accumulators held in registers.

```cpp
const float* xin = &in_nhwc[p*Cin];          // Cin contiguous floats
for (int co = 0; co < Cout; co += 4) {
    float a0=0,a1=0,a2=0,a3=0;
    for (int ci = 0; ci < Cin; ++ci) {        // unit-stride, vectorizable
        float x = xin[ci];
        a0 += x*w0[ci]; a1 += x*w1[ci];
        a2 += x*w2[ci]; a3 += x*w3[ci];       // x reused 4×
    }
    /* store a0..a3 */
}
```

**Why this specific optimization.** The naive profile pointed straight at memory stalls, not
at a shortage of compute. The fix therefore had to change *how data is fetched*, not how
much arithmetic is done. Reshaping the per-pixel computation into a contiguous dot product
turns the whole op into a cache- and SIMD-friendly GEMM — exactly how real inference
engines and NN accelerators lay out pointwise convolutions.

**System/hardware insight that led to it.** Caches move data in 64-byte lines and the
prefetcher rewards unit-stride access. A reduction whose stride is one cache line per step
(naive) wastes ~15/16 of every line and defeats prefetching; making that same reduction
contiguous lets one line serve 16 consecutive MACs, lets the prefetcher stream ahead, and
lets the compiler emit packed FMA instructions. Register blocking then raises **arithmetic
intensity** (FLOPs per byte loaded) so the FMA units stay busy → higher IPC.

**Profiling results (optimized):**

| Metric | Value |
|---|---|
| Runtime | ~1.0 s |
| Cycles | `‹perf›` |
| Instructions / IPC | `‹perf›` (expected: higher IPC) |
| L1-dcache load misses | `‹perf›` (expected: much lower) |
| LLC load misses | `‹perf›` (expected: much lower) |

**Expected or surprising?** The direction (faster, fewer misses, higher IPC) was expected.
The *magnitude* — a ~6× speedup from a pure layout change with zero algorithmic change —
is the kind of result that surprises people who assume O(N³)-style work is "compute bound."
It is a concrete reminder that on modern hardware, **memory layout often matters more than
instruction count**.

## 4. Comparison of the two profiles

| Metric | Naive | Optimized | Change |
|---|---|---|---|
| Runtime | ~6.4 s | ~1.0 s | **~6.3× faster** |
| L1-dcache load misses | `‹perf›` | `‹perf›` | ↓ large |
| LLC load misses | `‹perf›` | `‹perf›` | ↓ large |
| IPC | `‹perf›` | `‹perf›` | ↑ |
| Instructions | `‹perf›` | `‹perf›` | ↓ (vectorized) |

**Reasoning / why the gain makes sense.** Both versions perform the identical
`Cout·Cin·H·W ≈ 4.3 × 10⁹` multiply-accumulates. The naive version stalls because nearly
every MAC waits on a cache line fetched from a distant address, and most of each fetched
line is discarded. The optimized version fetches the same data in long contiguous streams:
the prefetcher hides DRAM latency, each cache line feeds many MACs, and the loop vectorizes
into packed FMAs. So we expect the cache-miss counters to collapse and IPC to rise, with
runtime dropping accordingly — which is exactly what the measurements show. The speedup is
not from doing less work; it is from **feeding the same work to the CPU at the rate the
memory system can actually sustain**.

## 5. Approaches considered / dropped

- **Compiler flags only.** Raising to `-O3 -march=native` on the naive code helped little —
  the bottleneck is the access pattern, which the compiler cannot legally reshuffle. This is
  why both versions share the same flags: to isolate the layout effect.
- **Small problem size.** At `64×64` the whole working set fits in cache and the two
  versions run within ~1× of each other. I kept the larger size precisely so the cache
  effect is observable — the contrast itself is part of the lesson.
- **Full GEMM tiling (blocking both pixels and channels).** Would push performance further
  toward a BLAS library, but it muddies the single, clearly-explainable insight (layout +
  reuse) that this assignment rewards, so I left it as future work.
